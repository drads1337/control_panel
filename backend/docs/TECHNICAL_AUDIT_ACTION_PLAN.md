## 🔴 Критические проблемы (High Priority)

### 1. SSRF уязвимость в webhook validation
**Файл:** `backend/services/webhooks/webhook_service.py:855`  
**Проблема:** Использование `socket.gethostbyname()` уязвимо к DNS rebinding атакам (TOCTOU)  
**Решение:** Использовать библиотеку с защитой от DNS rebinding или валидировать на уровне сокета  
**Статус:** ✅ **ИСПРАВЛЕНО**

**Выполнено:**
- Заменен `socket.gethostbyname()` на `socket.getaddrinfo()` для получения всех IP адресов
- Добавлена валидация всех IP адресов (IPv4 и IPv6)
- Добавлена блокировка IP адресов в URL (требуется hostname)
- Улучшена защита от DNS rebinding атак

### 2. Async функции в синхронном Flask
**Файлы:** 
- `backend/routes/chat.py:56` - `async def send_message()`
- `backend/routes/heartbeat.py:75` - async wrapper в декораторе

**Проблема:** Flask синхронный, async функции могут работать некорректно с WSGI (Gunicorn)  
**Решение:** 
- Убрать async из Flask routes
- Использовать `asyncio.to_thread()` или Celery для асинхронных операций
- Или мигрировать на Quart/FastAPI если требуется нативная асинхронность

**Статус:** ✅ **ИСПРАВЛЕНО**

**Выполнено:**
- `chat.py`: Заменен async `telegram.Bot` на синхронный HTTP API через `requests`
- Убрано создание новых event loops для каждого запроса
- Удалены неиспользуемые импорты `asyncio` и `telegram`
- Используется тот же подход, что и в `webhook_service` для консистентности
- `heartbeat.py`: Декоратор поддерживает async, но route синхронный - ✅ OK

**Результат:**
- ✅ Нет создания новых event loops
- ✅ Синхронный код в синхронном Flask
- ✅ Лучшая производительность
- ✅ Консистентность с остальным кодом

### 3. UserActivity в основной БД
**Файл:** `backend/services/activity/activity_service.py:278`  
**Проблема:** Логи пишутся напрямую в PostgreSQL, что может "взорвать" БД при высокой нагрузке  
**Решение:** 
- Вынести логи в очередь (Kafka/RabbitMQ) → Writer → OLAP хранилище (ClickHouse/TimescaleDB)
- Или использовать существующий AnalyticsBufferService для буферизации

**Статус:** ✅ **ИСПРАВЛЕНО**

**Выполнено:**
- Изменена логика по умолчанию: теперь используется буферизация вместо прямых записей
- Убрана сложная адаптивная проверка нагрузки - буферизация используется всегда (если включена)
- Прямые записи оставлены только для критических действий (через параметр `use_direct_write=True`)
- Упрощен код - удален метод `_check_system_load()`
- Автоматический fallback на прямые записи, если буферизация недоступна

**Результат:**
- ✅ Защита БД от перегрузки логами активности
- ✅ Использование существующего AnalyticsBufferService (write-behind pattern)
- ✅ Упрощенный и более надежный код
- ✅ Сохранена обратная совместимость

## 🟡 Важные улучшения (Medium Priority)

### 4. Custom Crypto Protocol
**Файлы:** 
- `backend/services/connect/connect_service.py`
- `backend/services/auth/challenge_service.py`
- `backend/utils/secure_crypto.py`

**Проблема:** Самописный протокол шифрования payload'а вместо стандартных решений  
**Решение:** 
- Заменить на JWE (JSON Web Encryption) для шифрования на прикладном уровне
- Использовать стандартный TLS (уже есть) + JWE если нужно дополнительное шифрование

**Статус:** 📋 **ПЛАН СОЗДАН**

**Анализ:**
- Текущая реализация использует AES-256-GCM (безопасно)
- mTLS уже обеспечивает защиту на транспортном уровне
- Custom протокол работает, но требует стандартизации

**План миграции:**
- Создан документ `CUSTOM_CRYPTO_MIGRATION_PLAN.md` с детальным планом
- Рекомендуется постепенная миграция на JWE
- Текущая реализация достаточна для production-ready статуса

**Приоритет:** Medium (не блокирует production-ready, но важно для долгосрочной поддержки)

### 5. Monitor_load декоратор
**Файлы:** `backend/middleware/load_monitoring.py`  
**Проблема:** Декоратор делает запись в Redis на каждый запрос (push model)  
**Решение:** 
- ✅ Уже заменен на prometheus-flask-exporter (pull model)
- Удалить неиспользуемый код или оставить для backward compatibility

**Статус:** ✅ **ИСПРАВЛЕНО**

**Выполнено:**
- Упрощен декоратор `monitor_load` до no-op (не делает ничего)
- Удалена вся ненужная логика (async/sync wrappers, error handling)
- Декоратор оставлен для backward compatibility (можно безопасно удалить из routes)
- Все метрики собираются автоматически через PrometheusMetrics из prometheus-flask-exporter

**Результат:**
- ✅ Нет overhead от декоратора (no-op)
- ✅ Упрощенный код (с 63 строк до 25 строк)
- ✅ Сохранена обратная совместимость
- ✅ Метрики собираются автоматически через PrometheusMetrics

### 6. Секреты через config_setup.py

**Проблема:** Генерация .env скриптом - уровень pet-проекта
